# Онлайн-доска для уроков: спецификация v0.2

*7 ноября 2026 (обновлено в T2.5 / T2.5b / T2.5c). Для передачи ИИ-агентам: скачать как Markdown и положить в репозиторий как SPEC.md.*
*(Примечание: во внешнем документе спецификации `Онлайн_доска_для_уроков_спецификация_v0_2.md` в разделе 2 и 5 указано прежнее значение `10 секунд` и таблица `meta`; владелец синхронизирует внешний документ вручную).*

## 1. Цель

Своя бесплатная доска вместо Miro для онлайн-уроков двух преподавателей (владелец и друг). Обычно урок идёт 1 на 1, на схемах и архитектурах бывает до 5 человек на доске; ученики в разных городах РФ. Нужны схемы и архитектуры, базовые фигуры, рукописный ввод (стилус, мышь, тачпад) и сохранение досок по ученикам. Вход на доску по ссылке, без регистрации учеников.

## 2. Решения и допущения

Решено владельцем:

- Основа: Excalidraw (лицензия MIT). tldraw не использовать из-за лицензии.
- Два преподавателя. Ученики и доски раздельные: каждый видит только своё.
- Кабинет только у преподавателей (ученики, доски, заметки и домашние задания). Ученикам кабинет не нужен: они заходят по ссылке на доску и вводят ник, он запоминается в браузере. В продакшене корневая страница `/` не генерирует случайные доски, а выводит подсказку «Откройте ссылку на доску, которую вам прислал преподаватель».
- Доступ к доске по ссылке без пароля. У досок есть ID. Об учениках храним только ник, ФИО и контактов нет нигде.
- Содержимое доски сохраняется на сервере снимком целиком раз в 5 секунд по умолчанию (`SAVE_INTERVAL_MS=5000`, в продакшене зажимается в диапазоне 2–8 с, так как порог перехода неактивного Durable Object в WebSocket Hibernation составляет 10 секунд, а запланированный `setAlarm` не блокирует гибернацию), только если были изменения, а также немедленно при любом закрытии или ошибке WebSocket-соединения, если есть несохранённые изменения (`dirty`).
- Синхронизация курсоров и штрихов не чаще 10 Гц.
- Режим пера (`penMode`): по умолчанию находится в состоянии «авто» (выключен, можно рисовать пальцем; автоматически включается при первом касании стилусом `pointerType === "pen"` и остаётся переключаемым вручную; касания пальцем по тулбару Excalidraw и двупальцевый зум/пан никогда не блокируются; защита от касаний ладонью по размеру контакта `>= 48px` работает всегда).
- Откат по версиям не нужен, только встроенные undo и redo.
- Копии досок в Git с возможностью выгрузки и обратного импорта.
- Пока без своего домена: бесплатные поддомены Cloudflare. Один приватный репозиторий GitHub, деплой через GitHub Actions.
- MCP во второй фазе: должен уметь делать с досками всё, что делает человек.
- Режим слежения, таймер и отдельные инструменты ведения урока не делаем (лазерная указка уже есть в Excalidraw).

Допущения (владелец может поправить):

- Один Worker раздаёт и статику, и API (Workers Static Assets). Актуальный рекомендуемый вариант Cloudflare проверить по документации, допустим Pages.
- Запасной путь, если Cloudflare недоступен ученикам: один VPS в РФ с Docker. Слои кода делим так, чтобы переезд был возможен.
- Без сквозного шифрования комнат: нужны хранение и бэкап на сервере.
- Интерфейс на русском.
- При обрыве связи клиент продолжает рисовать локально и синхронизируется после переподключения.

## 3. Жёсткие ограничения

- Только бесплатные лимиты Cloudflare. Workers: 100 000 запросов в сутки. Durable Objects (SQLite): 100 000 запросов, 13 000 ГБ·с вычислений, 100 000 записанных и 5 млн прочитанных строк в сутки, 5 ГБ на аккаунт, 1 ГБ на объект, строка или BLOB не больше 2 МБ. D1: 5 млн прочитанных и 100 000 записанных строк в сутки, 5 ГБ на аккаунт, 500 МБ на базу.
- 20 входящих WebSocket-сообщений считаются за 1 запрос. Удаления и setAlarm считаются записями, запись индекса считается ещё одной строкой. Лимиты сбрасываются в 00:00 UTC (03:00 по Москве), после превышения операции падают с ошибкой. Не ясно, считаются ли записи Durable Objects и D1 вместе, поэтому проектируем с запасом.
- Потолок размера одной доски: не более **20 000 элементов** (`MAX_BOARD_ELEMENTS = 20_000`) и не более **20 МиБ JSON снимка** (`MAX_SNAPSHOT_BYTES = 20 * 1024 * 1024`). При превышении `scene_update` отклоняется, а клиенту отправляется `{"type":"error","code":"board_too_large"}`.
- R2 не используем: для включения обычно нужна банковская карта.
- Зависимости только MIT, Apache-2.0 или BSD (плюс ISC). Репозиторий-образец без явной лицензии не копировать, только читать как пример.
- Доступность из РФ проверяется на пилоте. Бесплатный поддомен может не открываться у части провайдеров, поэтому адрес сайта задаётся настройкой, чтобы позже перейти на свой домен без переделки.

## 4. Архитектура

Браузер (React и @excalidraw/excalidraw) обращается к одному Worker: он раздаёт статику, принимает API-запросы и передаёт WebSocket в Durable Object «Board». Объект держит состояние доски в памяти, пишет снимок в свою SQLite и использует WebSocket Hibernation API. Список преподавателей, учеников и досок живёт в D1. Резервные копии уходят в приватный GitHub-репозиторий. MCP-сервер (вторая фаза) подключается к доскам как ещё один клиент по тому же протоколу.

Референс: репозиторий backpine/learn-durable-objects (Excalidraw на Workers и Durable Objects, учебный проект). Перед использованием кода проверить лицензию, без лицензии писать самим.

## 5. Модель данных

D1:

- teachers: id, name, token\_hash, created\_at
- students: id, teacher\_id, nickname, notes, archived, created\_at. Ученик это только ник и список досок у преподавателя, учётной записи у него нет.
- boards: id, teacher\_id, student\_id (может быть пустым), title, notes, created\_at, updated\_at, last\_backup\_at, deleted\_at

Все запросы фильтруются по teacher\_id. Преподаватель не видит данные другого.

SQLite внутри Durable Object доски:

- snapshot: chunk\_idx (`INTEGER PRIMARY KEY`), data (BLOB до 900 КБ), JSON сцены кусками (`{"v":1,"elements":[...]}`)
- snapshot\_backup: chunk\_idx (`INTEGER PRIMARY KEY`), data (BLOB), backed\_up\_at (`INTEGER`) — резервная таблица, куда при обнаружении ошибки разбора JSON (`snapshot_load_error`) автоматически копируются повреждённые куски (событие `snapshot_corrupted_backup_saved`). Если резервная копия записана успешно, объект стартует с пустой сценой и продолжает сохранять новые правки в `snapshot`. Если записать резервную копию не удалось, поднимается флаг `snapshotSaveBlocked`, блокирующий перезапись `snapshot`, а при `hello` клиенту отправляется `{"type":"error","code":"board_not_saved"}`.
- files: file\_id, chunk\_idx, mime, data (BLOB до 1 МБ), created\_at, last\_referenced\_at

Элементы живут в памяти как карта id в элемент. Снимок пишется только при изменениях, не чаще `SAVE_INTERVAL_MS` (по умолчанию 5 с, чтобы `alarm()` срабатывал до 10-секундного порога гибернации), а также немедленно при любом закрытии или ошибке WebSocket-соединения, если `dirty === true`. Таблица `meta` при сбросе снимка не пишется (`board_id` хранится в `WebSocketAttachment`, а `chunk_idx INTEGER PRIMARY KEY` является алиасом `ROWID` без отдельного индекса). При каждом сбросе объект сверяет дайджест (`computeChunkDigest`) каждого куска с уже записанным в SQLite и выполняет `INSERT OR REPLACE INTO snapshot` **только для изменившихся кусков**, а новые дайджесты и число кусков фиксируются в полях объекта только после успешного завершения `transactionSync`; запрос `DELETE FROM snapshot WHERE chunk_idx >= ?` выполняется только при уменьшении числа кусков. Вторичных индексов на этих таблицах нет.

## 6. API и протокол (контракт)

Преподаватель входит по личному токену: заголовок Authorization: Bearer \<TOKEN>. Токены хранятся хэшами, выдаются вручную владельцем.

- POST /api/students {nickname}; GET /api/students; PATCH /api/students/:id {notes, archived}
- POST /api/boards {title, student\_id?, from\_board\_id?} возвращает {id, url}; from\_board\_id клонирует прошлую доску
- GET /api/boards?student\_id=; PATCH /api/boards/:id {title, notes}
- DELETE /api/boards/:id: мягкое удаление, окончательное через 30 дней
- POST /api/boards/:id/restore: из загруженного .excalidraw или из копии в Git
- GET /api/backups?student\_id=: список копий из Git
- GET /ws/:id?nick=<ник>: WebSocket доски, без токена, ID неугадываемый. До появления реестра досок в D1 (T3): если `ALLOW_ANY_BOARD_ID=true` (только для локальной разработки), пускает на любой валидный ID; иначе (на пилоте) требует, чтобы ID входил в секрет `PILOT_BOARD_IDS` (список до 50 валидных 22-символьных base62 ID через запятую), иначе возвращает `404`.
- PUT и GET /api/boards/:id/files/:fileId: картинки, доступ по ID доски
- GET /api/health

ID доски: 128 бит случайности, 22 символа base62.

Сообщения WebSocket (JSON): hello {client\_id, nick}, в ответ snapshot {elements, collaborators}; scene\_update {elements: \[изменённые\]}; cursor {x, y, pointer, tool}; ping; серверные ошибки `error {code: "board_too_large"}` (при превышении 20 000 элементов или 20 МиБ снимка) и `error {code: "board_not_saved"}` (при `hello`, если снимок повреждён и не удалось сохранить `snapshot_backup`). Конфликты клиенты решают через reconcileElements Excalidraw (version и versionNonce), сервер хранит элемент с большей version. Удалённые элементы остаются с is\_deleted=true и чистятся через 30 дней.

## 7. Картинки

Как устроено в Excalidraw: элемент-картинка хранит только fileId, а данные лежат в отдельной карте files (dataURL), id по умолчанию это SHA-1 файла. Максимальный размер файла 4 МиБ. Карта files может содержать файлы, на которые ничто не ссылается, поэтому перед сохранением её сверяют с элементами.

План:

1. До загрузки уменьшаем картинку (длинная сторона не более 1600 px) и пережимаем в WebP или JPEG, качество около 0,8. Сначала проверить, что Excalidraw уже делает сам.
2. Передача бинарным PUT (не base64), id равен SHA-1 содержимого: дубликаты не хранятся.
3. Worker кладёт файл в объект доски порциями до 1 МБ в таблицу files (одна строка на порцию, в бюджет записей укладывается).
4. Лимиты: файл до 4 МиБ, на доску до 100 МБ картинок. При превышении понятная ошибка.
5. GET отдаёт файл с Cache-Control: immutable.
6. Сборка мусора по alarm: файлы, на которые 30 дней не ссылается ни один элемент, удаляются.
7. В резервную копию (.excalidraw) картинки входят в ключ files.

## 8. Бюджет запросов и записей

Запросы = люди × сообщений в секунду × доля активности × секунды / 20, плюс HTTP-вызовы (около 5–10%). Урок 1,5 часа:

- 1 на 1 (2 человека, 10 сообщений/с, активность 30%): 32 400 сообщений, около 1 620 запросов, до лимита около 60 уроков в сутки.
- 5 человек, реалистично (10/с, активность 30%): около 4 050 запросов, около 24 уроков в сутки.
- 5 человек, тяжело (10/с, активность 100%): около 13 500 запросов, около 7 уроков.
- 5 человек без ограничения частоты (30/с, активность 100%): около 40 500 запросов, около 2 уроков. Поэтому ограничение частоты обязательно.

Записи строк (пересчитано в T2.5 / T2.5b после отказа от записи `meta`, перехода на `SAVE_INTERVAL_MS=5000` и записи только изменившихся кусков):
- Снимок до 900 КБ (1 чанк в `snapshot` с `INTEGER PRIMARY KEY` без вторичных индексов) стоит **ровно 1 строку SQLite за сброс** (+ 1 тарифицируемая запись `setAlarm`, итого 2 тарифицируемые записи за сброс). Для крупных многочанковых досок (> 900 КБ) переписываются только те куски, в которых изменились данные.
- При сбросе раз в 5 секунд (`SAVE_INTERVAL_MS=5000`) и реалистичной доле рисования 30% за 1,5-часовой урок (1 620 активных секунд) выполняется не более 324 сбросов = **324 строки в `snapshot`** (около 648 тарифицируемых записей с учётом `setAlarm`), чего хватает примерно на **150 уроков в сутки** в рамках бесплатного лимита 100 000 записей.
- Даже при 100% непрерывном рисовании весь 1,5-часовой урок (1 080 сбросов за 5 400 с) это **1 080 строк в `snapshot`** (2 160 тарифицируемых записей с `setAlarm`), то есть запас более **45 уроков в сутки**. Без сглаживания (запись каждого сообщения при 10 Гц) один рисующий выбирает сутки за 2,8 часа.

Это оценка, а не измерение. На пилоте сверить с панелью Cloudflare.

Требования:

- Курсор и штрихи не чаще 10 Гц, чужие курсоры интерполировать на клиенте. Курсоры на диск не пишем.
- scene\_update батчить не чаще 10 Гц, в процессе рисования слать промежуточные состояния, финальное при отпускании. Неизменившееся не слать, ping не чаще раза в 30 секунд.
- Снимок только при изменениях; немедленный сброс при закрытии/ошибке любого соединения, если `dirty === true`; запись только изменившихся кусков; без вторичных индексов на горячих таблицах; updated\_at в реестре обновлять не чаще раза в 10 минут.
- Логировать число сообщений и записей на доску; показывать баннер при приближении к лимиту.

## 9. Экспорт, копии и импорт

Форматы из редактора:

- SVG: векторный, подходит для схем и архитектур, в него можно вшить редактируемую сцену. Проверить шрифты: если текст зависит от внешнего шрифта, у зрителя он может отобразиться другим.
- PNG: масштаб 1x–3x, сцену тоже можно вшить. Самый надёжный вариант для отправки ученику.
- .excalidraw: полная доска со всеми картинками.
- PDF: в редакторе нет, делаем через печать браузера или клиентскую библиотеку (проверить).

Экспорт на сервере без браузера сложен (нужно окружение браузера). В MVP экспорт только кнопками в браузере, в Git лежит .excalidraw. Серверный экспорт для MCP решаем во второй фазе.

Копии в Git: через 10 минут без активности (alarm) доска, изменённая с прошлой копии, выгружается как boards/<преподаватель>/<ник>/<ГГГГ-ММ-ДД>\_\<id>.excalidraw в приватный GitHub-репозиторий. Лучше отдельный репозиторий для копий, чтобы история с картинками не раздувала репозиторий кода. Токен: fine-grained PAT только на этот репозиторий, секрет Worker.

Импорт: любой .excalidraw открывается в редакторе вручную. POST /api/boards/:id/restore создаёт доску из загруженного файла или из копии в Git: с тем же ID, если он свободен, иначе с новым; картинки раскладываются обратно в files. Лимиты GitHub API на размер файла проверить при реализации.

undo и redo встроены в Excalidraw, это клиентская история, после перезагрузки страницы она пропадает. Поведение при совместной работе проверить двумя клиентами.

## 10. Безопасность и приватность

- Секреты (хэши токенов, GitHub-токен, токен Cloudflare для Actions с минимальными правами) только в секретах Worker, секретах GitHub и .env, не в репозитории и не в чате с ИИ.
- Ссылка на доску даёт доступ на запись. Ник вводится при входе и личность не подтверждает.
- В названиях досок и папок только ники. ФИО, контактов и сторонней аналитики нет.
- Ограничить размер входящих сообщений (2 МиБ), размер снимка доски (20 000 элементов / 20 МиБ), число подключений на доску (не более 20) и частоту создания досок.
- Если позже появятся персональные данные, перепроверить требования закона о локализации данных россиян (это не юридическая консультация).

## 11. MCP (вторая фаза)

Цель: делать с досками всё, что делает человек. MCP-сервер это ещё один участник доски («ИИ») по тому же WebSocket-протоколу и тот же REST API. По возможности без отдельного Durable Object (без состояния, Streamable HTTP), чтобы не тратить квоты. Авторизация: отдельный отзываемый токен на клиента, привязанный к преподавателю.

Инструменты:

- Администрирование: поиск ученика по нику, список досок, создание, восстановление из копии.
- Сцена: прочитать доску структурированно (элементы, тексты, связи), добавить, изменить и удалить элементы, добавить картинку.
- Схемы: draw\_diagram (узлы, связи, направление) с автораскладкой. Библиотеку раскладки проверить на размер и работу в Worker. Конвертации Mermaid на сервере, насколько известно, нет (нужен браузер), поэтому либо очередь на открытый клиент, либо готовый JSON элементов от агента.
- Экспорт: .excalidraw сразу, SVG и PNG через серверный рендер (способ выбрать во второй фазе).

Безопасность: содержимое доски это недоверенные данные, а не инструкции (ученик может написать на ней текст для агента). Разрушающих инструментов (удаление доски) нет, правки помечаются автором «ИИ», вызовы пишутся в журнал.

## 12. Задачи для ИИ

Порядок: T0, затем T1 и T2 параллельно, затем T2.5, затем T3, T4, T5, T6, T7, пилот, потом T8 и T9. Каждая задача в отдельной ветке и отдельном pull request. Два ИИ не правят одни и те же файлы одновременно. Контракт (разделы 5, 6, 9) меняется только вместе с правкой этого файла.

## 13. Правила для всех ИИ (AGENTS.md)

1. Сначала прочитай SPEC.md и не расширяй задачу.
2. Не меняй контракт (разделы 5, 6, 9) без правки SPEC.md и пометки в PR.
3. Новые зависимости только под MIT, Apache или BSD, перечисляй их в PR. tldraw нельзя.
4. Секреты не в коде и не в логах.
5. К каждой функции тест или ручной сценарий проверки в PR.
6. Маленькие коммиты с понятными сообщениями.
7. Если требование неясно, не угадывай: оставь вопрос в PR.
8. Не пиши, что работает, пока не запустил; в PR укажи, что именно проверено.
9. Лимиты и цены платформ сверяй с актуальной документацией, не с памятью.

## 14. Открыто, проверяем на пилоте

- Открывается ли бесплатный поддомен и синхронизируется ли доска у учеников из разных городов и сетей. Если нет: свой домен или VPS.
- Реальный расход запросов и записей за неделю (панель Cloudflare).
- Стилус, ладонь и тачпад на реальных устройствах; режим пера; undo и redo при совместной работе.
- Шрифты в SVG, способ PDF-экспорта.
- Лицензия референс-репозитория; лимиты GitHub API на размер файла.
- Поведение при обрыве связи и переподключении.
